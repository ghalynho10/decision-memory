## Minor

### 🟡 The oracle got strictly stricter after the live run that ticked `verify.md`, `docs/specs/0009-proven-correctness-evaluation-harness/verify.md:21`

**Problem**: The round-3 co-location fix changed what query 1 and assertion A require. Query 1 used to pass when the answer cited `DM-0012` *and* some citation somewhere carried a `decision.alternatives[` value path; it now requires that path to belong to a `DM-0012` citation. `verify.md:21` still states the old rule verbatim ("cites `DM-0012`, **and** at least one citation carries a `decision.alternatives[*]` value path"), and its `[x]` — along with assertion A's at line 26 — was earned by the 2026-08-12 live run recorded at the bottom of the file, which predates commit `0b5e1bf`. The fix commit touched neither `verify.md` nor the scope row that cites it. Nothing in the diff re-ran the battery.

**Why it matters**: This is the feature whose entire product is trustworthy pass/fail evidence, and the scope row is marked `done` on the strength of this checklist. Two ticks now describe a rule the code no longer applies, and the stricter rule is exactly the kind that can flip a marginal live PASS to FAIL — that was the point of tightening it. Carrying the ticks forward is the failure mode the harness exists to prevent.

**Suggested fix**: Re-run `uv run --env-file .env decision-memory evaluate <jobpilot>` once against the current code, update the two ticks to whatever it actually reports, and reword line 21 to state the co-location rule ("cites a `DM-0012` chunk whose value path is `decision.alternatives[*]`"). Update the "Known state" paragraph's counts to match.

### 🟡 `verify.md` calls the column-swap regression "unit locked"; it is not, and CI never runs it, `docs/specs/0009-proven-correctness-evaluation-harness/verify.md:32`

**Problem**: The regression-lock line says the `active_chunks` value_path/fingerprint swap is "unit locked in `test_store_format.py::test_active_chunks_keeps_value_path_and_fingerprint_separate`". That test carries `@pytest.mark.integration`. I confirmed it is excluded from the default suite (`481 passed, 18 deselected`) and that naming it explicitly still yields `1 deselected` — it only runs under `-m integration`. AGENTS.md is explicit that "CI on push runs pre commit checks plus the unit suite only", so the lock never runs on the push gate. `docs/scope/scope.md:160` repeats the same "unit locked" phrasing about the feature as a whole.

**Why it matters**: The column swap (`index_reader.py:140-141`) is the one genuine production bug this branch fixes — it silently corrupted every citation's `value_path` and broke the `--value-path` filter against a real store. A reintroduction would pass the push gate today. Separately, the doc asserts a coverage property the repo does not have, which is how a gap gets forgotten.

**Suggested fix**: Either correct both lines to say "integration locked, not run in CI" (the honest, cheap option, consistent with round 3's accepted reasoning about the file's marker convention), or add a fast-suite companion that exercises the descriptor mapping without a real store so the push gate actually catches a re-swap. The test's own docstring defends the marker choice well; it is only the two docs that overclaim.

### 🟡 `proposed_record_ids` is still untested, and the empty-set guard only catches total loss, `src/decision_memory/infrastructure/evaluation_runner.py:196`

**Problem**: Round 3 named this as the one test it would ask for; the fix batch added ten tests to `test_evaluation_runner.py` and none of them covers `proposed_record_ids`. The commit also *changed* the method (dropped the narrowing `assert`, folded the `id is not None` check into the filter), so this is changed branching logic shipping without a test — glob, parse-failure skip, status filter, and id-`None` skip all decide query 3's oracle and none is exercised at any level. `TESTS = configured`, so that is a finding on its own.

The second half is a residual hole in the round-3 fix. `_satisfies` fails when `proposed` is empty, but not when it has merely *shrunk*. I verified with a scratch probe: a fixture with `cite_all_proposed=True` and `proposed = {"DM-0015"}` passes on an answer citing only `DM-0015`, whether or not three other proposed records silently failed to parse. Since `proposed_record_ids` drops unparseable files without a sound (a deliberate choice, correctly reasoned in its docstring), a partial parse regression weakens query 3's oracle instead of failing it — the same false-positive family, one notch smaller.

**Why it matters**: Query 3 is a named Done-when gate. The empty-set guard makes the total-failure case loud; the partial case is the more likely one (one adapter change, one malformed record) and stays silent.

**Suggested fix**: Add unit tests for `proposed_record_ids` against a small records directory (a proposed record, a ratified one, an unparseable file, a non-record `.md`) — it is pure filesystem-plus-parse logic and needs no provider. Then give the port a way to report how many record files it could not parse (a small result object, or a second port method) so `_satisfies` can fail the fixture when the proposed set was assembled from an incomplete read.

## Nits

- ⚪ `src/decision_memory/application/evaluation.py:69`, `QueryOracle`'s docstring still says each `required_value_path_prefixes` entry "must match at least one citation". After the co-location fix it must match at least one citation *of a required record*. This is the same docstring-overclaims-the-code defect round 3 raised against `run_query`, on the authoritative description of the oracle's semantics.
- ⚪ `src/decision_memory/application/evaluation.py:414`, the co-location branch keys only off `required_record_ids`. A fixture combining `cite_all_proposed=True` with a prefix falls into the loose any-citation branch even though the proposed set is semantically "the required records" — I confirmed such a fixture passes on an unrelated record's prefix. Unreachable in the shipped battery (query 3 has no prefixes), so this is a latent trap rather than a live bug, but it is the same hole the fix just closed.
- ⚪ `src/decision_memory/cli.py:1155` vs `:1170`, the two new guards use inconsistent criteria: `--records` warns on *any* non-empty directory, `--store` only when an active generation exists. `evaluate --store ~/some-populated-dir` scatters `ACTIVE`, `lock.db`, and a generation tree in silence. A `store_dir.is_dir() and any(...)` fallback would make the pair symmetric.
- ⚪ `src/decision_memory/infrastructure/store.py:133`, `read_active` swallows `OSError` and returns `None`, so a store whose `ACTIVE` file is present but unreadable gets no `--store` warning. Narrow, but it is the one false-negative path in an otherwise total check.
- ⚪ `src/decision_memory/cli.py:1213`, a mid-battery lock conflict discards every fixture already run and prints only the one-line message. Under `--runs 3` that can be several minutes of paid live queries thrown away. Printing the partial report before the message would keep the work.
- ⚪ `src/decision_memory/cli.py:1213`, the lock conflict exits `1`, the same code as "one or more fixtures failed", so a CI consumer cannot distinguish an infrastructure conflict from a real correctness failure. Consistent with `ingest`/`query`, so arguably correct — worth a deliberate decision rather than an inherited one.
- ⚪ `src/decision_memory/cli.py:1196`, `adapt failed with exit code N` carries no per-record detail, unlike `adapt_command`'s report. A corpus that fails to adapt gives the user a bare number to debug from.
- ⚪ `src/decision_memory/application/evaluation.py:393,399`, `missing` is bound twice to two different sets within `_satisfies`. Harmless today; distinct names would keep it that way as the function grows.
- ⚪ `docs/scope/scope.md:160`, still says "456 unit passing"; the suite is 481. Round 3 flagged this at 473 and it was deferred to `/sync`; it has since drifted further.
- ⚪ `src/decision_memory/cli.py:1114-1217`, `evaluate_command` is ~100 lines covering four validations, two warnings, path resolution, adapt, ingest, the battery, and its own error mapping. Still linear and well commented, but the records/store resolution block would read better as a helper returning the two paths.

## Strengths

- **The round-3 fixes are correct, complete, and each one landed with the right kind of test.** The two oracle fixes are locked by tests that assert the *old* behaviour is gone (`test_value_path_prefix_must_belong_to_a_required_record` constructs precisely the citation pair that used to pass), not merely that the new behaviour works. That is the durable form, and it is now consistent across three rounds of fixes.
- **The `LockError` fix was placed by architecture, not by convenience.** The obvious patch — catching it in `_run_query_fixture` — would have dragged an infrastructure exception into the application layer. Putting it in the CLI alongside the two commands that already handle it keeps the dependency rule intact and makes the three handlers read identically, and the docstring was corrected to match rather than left to drift.
- **The harness earned its keep before it merged.** `index_reader.py:140-141` is a real bug in shipped query code — value_path and fingerprint read from swapped columns — that no unit test, no verify run, and three prior review rounds had caught. A correctness harness whose first act is to find a correctness bug is the strongest possible argument for the feature.
- **The comments encode the review history.** The `--runs` cap, the first-failing-detail choice, the `runs >= 1` raise, the empty-proposed guard, the co-location rationale, the early path print, the integration marker — each carries a *why* that names the finding it came from. A future editor cannot silently undo any of them, which is why four rounds of fixes have not accumulated into mush.
- **The docs still refuse to flatter the result.** `verify.md` leaves the carried-in gates unticked, and the scope correction retracts an earlier over-claim after measuring 12 runs rather than defending it. My two documentation Minors are about staleness and one wrong word, not about spin.

The remaining gaps, in order of what I would actually ask for:

1. `proposed_record_ids` — untested at any level, changed by this commit, pure filesystem logic that decides query 3's oracle (Minor 3).
2. The column-swap regression lock does not run in CI (Minor 2).
3. `EvaluationRunner._chunk_ids` is stubbed in every unit test and exercised only by the env-gated live suite; `run_query` legitimately needs live providers, so that one is fine as is.
